# WordPress Connector: MCP, OAuth and site-management comparison

**Research date:** 2026-10-18
**Source baseline:** \`Yolol100/wordpressconnector\` \`main\` at \`0e25b052c209df0dc24bcd1b00ae4c3f4cfa00d9\`, released source \`1.19.17\`.
**Evidence boundary:** GitHub and public upstream documentation are code/vendor evidence; successful GitHub CI does **not** mean a new version is installed on any owner's live site. The last authorized ISOHULK checks previously verified **1.19.16** installed and read-only GitHub OIDC, not direct OAuth or production write permission.

## 1. Evaluation criteria

A genuine "install plugin, connect ChatGPT, ask it to edit WordPress" experience needs all six independent capabilities:

1. **Discovery/transport:** publicly reachable HTTPS streamable MCP with truthful version and method negotiation. The MCP endpoint must not be publicly executable without authentication.
2. **Interactive authorization:** ChatGPT-supported OAuth 2.1 with protected-resource and authorization-server metadata, authorization code + PKCE S256, exact client/redirect validation, issuer identification, audience/resource binding, refresh/revocation, login and consent for the *current* WordPress account.
3. **Real permissions:** per-user WordPress capabilities, plugin-native Abilities/REST permission callbacks, least privilege and per-action allowlists; no first-administrator impersonation or bypass.
4. **Action semantics:** small discover/inspect/execute tool surface, verified installed plugin providers, content and media CRUD, Elementor, block templates, WooCommerce, plugin/theme lifecycle; read-only/default-dry-run before confirmed writes.
5. **Recovery:** independent offsite **files + database** backup with completed test restore on staging; backups must not be guessed from "backup plugin installed" or WordPress's transient update-backup directory.
6. **Operational proof:** client-to-site authentication from a *real ChatGPT workspace*, 401/403 tests, tool scan, non-destructive live canary, target readback, then authorized staging write/rollback; clear revocation and audit.

## 3. Existing Connector inventory: confirmed in source

- WordPress plugin \`1.19.17\`, GPL-2.0-or-later and PHP >=7.4, with short-lived GitHub Actions OIDC for an approved pinned site.
- Private, authenticated \`/wp-json/webactueel-wordpress-connector/v1/mcp\` with compact discovery/actions/execute tools, modern and legacy MCP revisions, fixed resources and prompts.
- Existing semantic adapters for WordPress posts/media/users, Elementor Core/Pro, Yoast, WooCommerce, Gutenberg/Site Editor, plugins/themes/ZIP packages, safe filesystem subsets and approved third-party native Abilities.
- \`Runtime/Runner\` and \`Security/Policy\` implement mutation confirmation, dry-run, capabilities, fingerprints, sensitive/public-repo guards, request IDs and selected action rollback.
- WordPress administrator button creates an **Application Password** for clients able to use HTTP Basic Auth, but no ChatGPT-native OAuth login.
- \`ConnectionReadinessAdapter\`/admin guide detects HTTPS, pairing and a few active backup plugins, and correctly keeps \`oauth_21_ready\` and restore verification false.
- Public GitHub route is intentionally limited; plugin/theme/server writes in private REST/MCP require additional server flags and WordPress capabilities. No verified private ChatGPT OAuth session.
- There is no verified host-controlled staging/restore provider, no automatic file+DB offsite backup and no proven secure universal editor for every third-party plugin.

## 4. Targeted engineering decisions

| Gap | Engineering decision | Safety/release gate |
| --- | --- | --- |
| One-click ChatGPT onboarding | Make an **admin-only, credential-free "Test my MCP connection" browser button** and copyable canonical endpoint; label it honestly as an *in-session* REST/transport test, not a ChatGPT OAuth proof. | WordPress REST nonce, manage_options page, no secrets, deny unauthorized requests, real Docker UI test. |
| ChatGPT OAuth login | Build/adapt a **separately security-reviewed** OAuth 2.1 authorization bridge. It must use exact ChatGPT client and redirect identity, PKCE S256, user consent, scoped bearer tokens, refresh/revoke and per-user WordPress permission checks. Do **not** publish fake \`.well-known\` metadata if no real issuer exists. | Independent full flow from ChatGPT workspace, security review, wrong issuer/client/redirect/resource/scopes, token replay/revocation, 401, WAF/cache and rate limits. Open [#984](https://github.com/Yolol100/wordpressconnector/issues/984). |
| Generic plugin/Elementor coverage | Reuse \`wordpress.abilities\` and existing exact approved-provider source mapping. Let the site tell the assistant which real abilities exist. Add adapters **only for proven missing vendor APIs**, not generic function invocation. | Private plugin inventory, exact versions, native WordPress permissions, provider-specific staging fixtures. Open [#989](https://github.com/Yolol100/wordpressconnector/issues/989). |
| Reliable rollback | Integrate an independently authenticated offsite files+database backup provider, plus staging clone and verified test restore before dangerous server/theme work. | Never send archives/credentials to public GitHub; recovery evidence must cover host/database outage, not merely Core temp backup. Open [#988](https://github.com/Yolol100/wordpressconnector/issues/988). |
| Hosting/database | Separate authorized host control plane, starting with read-only limits and diagnostics. | No generic unrestricted PHP/SQL/shell or WordPress permission bypass. Open [#990](https://github.com/Yolol100/wordpressconnector/issues/990). |
| Multi-site management | Private owner-approved registry with per-site credential refs and revocation. | Exact site binding, multi-tenant checks, no public inventory. Open [#992](https://github.com/Yolol100/wordpressconnector/issues/992). |
| Safe writes | Existing policy/fingerprints/confirm/idempotency stay in one semantic Runner; communicate actual confirmation and rollback state. | WordPress permissions, explicitly enabled server flag, restore/checkout testing, independent readback; don't weaken public allowlist. |

## 5. Owner actions that no plugin can legitimately skip

1. A WordPress administrator revokes any Application Password revealed in screenshots or chat and keeps future secrets only in trusted credential UIs.
2. The ChatGPT Business/Enterprise/Edu workspace administrator must consent to adding/publishing a custom MCP plugin and complete OAuth in the browser. Installing a PHP plugin alone cannot alter ChatGPT workspace settings or permissions.
3. The site owner chooses an approved external backup/hosting provider, authorizes its account/site, stores DB+files independently and tests a **real** staging restore. These approvals cannot be obtained from plugin source or a GitHub CI run.
4. For high-risk writes the actual WordPress site must pass readback, plugin-version parity, capability checks and staging acceptance first.

## 6. Evidence ledger for this upgrade

- Public primary sources above: **researched**.
- GitHub code and policy comparison: **reviewed at named SHA**.
- Any new source changes: report exact PR and CI/test status separately.
- Authorized live deployment: **not demonstrated by research or GitHub CI**.
- WordPress MCP OAuth to ChatGPT: **not established** until actual user linking.
- Full backup plus restored staging site: **not demonstrated**.

**Outcome definition:** don't call the integration "connected" solely because a plugin is installed, GitHub Actions runs are green, an Application Password was generated, an MCP URL responds anonymously, or a connected plugin shows a green checkmark. The right evidence is a signed-in OAuth handshake plus authenticated \`tools/list\`/read-only canary and WordPress user identity readback on the exact site, and separately a staged write/rollback where approved.
